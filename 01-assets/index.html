Ontology Docs: Assets

This document serves to specify the Asset architecture and provide key definition for Application terminology.

Definition

An Asset is an image file.

Liberated Pixel Cup

LPC Assets are bundled with the Application by default.

Overview

The Asset directory (and all subdirectories) contains Asset Image Files (*.png) and Asset Property indices (*.yaml). The initialization reads in all of these files recursively and then use the Property indices to index each Asset file into the Registry. Each image file that appears in the Asset directories must be configured in a YAML file to get indexed and injected into the Application . The Property configuration in the *.yaml files must conform to the Asset Property schema of the respective Asset Category it is configuring.

Schema Merge

All *.yaml files in the Asset directories are merged into a single schema, so every key must be unique. If two image files have the same name, one of them will be overwritten during Registry indexing.

Asset: Concepts

Concept: Identity

IDs & Names

IDs are used to map Asset Files to images loaded into the Registry, to ensure each Asset is only loaded into the memory once, no matter how many times it is rendered in a single frame. In other words, IDs uniquely identify a physical Asset File, but not rendered entities.

Names are used to uniquely identify an instance of the Asset file. A single Asset ID may have multiple Names. A Name corresponds to a particular deployment of an Asset onto the Board.

In short, a Name identifies an Asset's deployment. A ID is what binds a deployed Asset to its image file.

Concept: Mutability

Properties & State

Properties are static and never changed by Mechanics. Properties determine the immutable characteristics of Assets, e.g. their dimensions and hitboxes. They are loaded side-by-side with the Asset files in the /src/assets/** directory. All Assets have, at bare minumum, a Dimension property, specifying their respective width and length, and a Priority property, that specifies the statically configured sort key for their relative rendering order. Dimension is a Cartesian coordinate (tuple), whereas Priority is an integer.

State is dynamic and can be changed by Mechanics. State determines the mutable characteristics of an Asset, e.g. the current Position of an Asset, the current Animation, etc. All Assets have: Position State, given as a Cartesian coordinate (tuple); a Layer, given as a categorical variable'; an Elevation, representing their Z-axis, given as an integer; an Anchor, used to augment the perspective-based render sorting, given as an integer.

Model: Mutators

  • parameters:
    • action: bool: The radius of the Asset's action.
    • vision: bool: The radius of Asset's vision.
  • triggers: Boolean flags.
    • animated: bool: Flag for receiving animation updates.
    • dead: bool: Flag for receiving Mechanic updates.
    • submerged: bool: Flag for receiving Frame channels.

Base Model: AssetProperties

  • dimensions: Dimensions: Asset Frame dimensions.
  • priority: int: Static ordinal render sort key.

All Asset Properties inherit fields from this model.

Base Model: AssetState

  • layer: str: Board Layer key.
  • elevation: int: The Z-axis of the Asset.
  • anchor: int: Offset for ground perspective render sort-key.
  • mutators: Mutators: General behavioral flags for rendering and logic.

All Asset States inherit fields from this model.

Concept: Animacy

Frames & Animations

A Frame represents the binding of an Asset to a particular partitioning of its raw image file into a Frame space. Frames expose interfaces for indexing the Frame space via Asset Properties, and they also expose interfaces for accessing Frame space via Asset State.

In other words, Asset Properties determine the metric used by the Engine to measure the Asset's Frame space, whereas Asset State determines where in its Frame space the Asset currently resides.

This is the reason for distinguishing Asset Categories and Asset Instances in the Hierarchy: Frames in a Sprite Sheet represent Actions, Frames in a Resource represent Lifespan Stages, Frames in an Effect represent Periodicity, etc. These are different stateful dispositions for an Asset to assume that are categorically distinct and manifest in the atlasing strategy used by the image file. This space is described by the particular configuration of an Asset's Properties, and furthermore, to exist on the Board, an Asset must have a strategy for associating its State with a particular Frame described by its Properties.

To extend the analogy, an Animation represents a strategy for navigating the Frame space over time. Animations project the internal State changes in an Asset onto a particular trajectory through its Frame space.

When an Asset implements an Animation, this is accompanied by its State possessing an animation field. The purpose of this field is to mutate over time and thus describe the trajectory of the Asset through its Frame space.

Model: AnimationState

  • action: Action key of Animation.
  • direction: Directiony key of Animation.
  • frame: Frame index of Animation.
  • tick: Engine tick accumulator. Used to control the speed of the Animation.

Concept: Physicality

Many Asset Categories have a Mass Property. Only Assets with Mass can participate in collisions and other kinematic events. In other words, An Asset's Mass determines its behavior within the physics of the game,

  • \(m > 0\): Dynamic Body. Participates in momentum calculations.
  • \(m = 0\): Static Body. Treated as having infinite mass (\(m \to \infty\)) in physical models. Its Velocity is unaffected by collisions, but its immobility forces dynamic Assets to resolve overlap.
  • \(m = -1\): Sensor. The Engine detects the spatial collisions for logical conditions, but ignores it entirely during collision resolution.

See SpatialMechanics for more information.

Concept: Appearance

Rendering

World rendering evaluates spatial geometry using discrete macro-elevations, intra-elevation substrate planes, ground perspective, and coplanar priority, known respectively as Elevation, Substrates, Perspective and Priority,

\[ \text{sort_key}(A) = \Big(A.\text{elevation},\; A.\text{substrate},\; \text{ground}(A),\; A.\text{properties.priority}\Big) \]
  1. Primary Key (A.elevation \(\in \mathbb{Z}_{\ge 0}\)): Discrete topological story or platform tier (0, 1, 2, ...).
  2. Secondary Key (A.substrate \(\in \mathbb{Z}_{\le 0}\)): Intra-elevation rendering plane within macro-elevation \(E\).
  3. Tertiary Key (ground(A) \(\in \mathbb{Z}\)): Continuous geometric perspective: \(\text{ground(A)} = \text{int}(A.\text{state.position.y} + A.\text{dimensions.l} + A.\text{state.anchor})\).
  4. Quaternary Key (A.properties.priority \(\in \mathbb{Z}\)): Coplanar tie-breaker declared on immutable AssetProperties.

See Rendering documentation for more information.

Substrates

Certain Assets have a dedicated Substrate to preserve the fidelity of their rendering order. These values are hydrated onto the Asset directly via MaterialIndex during hydration.

| Substrate | Dedicated Elevation | Assets | | Environ | -4 | tiles.environs | | Fluids | -3 | effects.fluid | | Surfaces | -2 | geography.shorelines, crafts.struts.floors, crafts.struts.paths, crafts.struts.flats | | Overlay | -1 | crafts.bridges, crafts.stairs, objects.doors, crafts.struts.solids, crafts.struts.stripes, crafts.struts.designs | | Standard | 0 | *|

!!! @TODO(07-04) This entire procedure needs re-evaluation now that Substrates are not Elevations, i.e. prior to Phase 07.04 Substrates were used to lazily-load Elevations. Now they are a dedicated partition of the sort key (elevation, substrate, ground, priority)

During CollisionMechanics and Perimeter generation, all negative Substrates are collapsed into elevation = 0, i.e. \(\text{elevation} \in [-\infty, 0] \to \text{elevation} = 0\), in order that all Assets on these Substrates may participate in collisions at elevation = 0.

Concept: Materiality

Many Assets have their Frame space defined over a Material partition. Material affects the color palette of an Asset and has other consequences in the Economy.

The Material Space is further subdivded into non-overlapping Genera,

Material Genera Enumerations
Ceramics clay
Chromatics neutral, blue, red, yellow, green
Geologics limestone, feldspar, granite, marble
Metallics copper, iron, gold
Organics cotton, thatches, wood

Each Genera refers to a range of Material Value. An Asset with the modality of Material declares a Genera in its Properties and then binds to a Material Value in its State. In other words, if an Asset indexes its Frame space over Material through its Properties, then its Asset State must specify which Material it should instantiate when deployed.

Chromatics, being a discrete shade of color, requires a Host Material, to accept its payload.

See Material documentation for more information.

Model: Material

  • genus: MaterialGenera: Partition of Material Space.
  • host: Optional[Union[Ceramics, Organics]]: Host Material for Chromatic Genera.

Asset: Hierarchy

While Assets are instantiated by injecting a common root class with component behaviors (see next section), the Assets which result from the Entity-Component-System (ECS) injection still conform to a strict hierarchy of Categories and Instances. The Property and State schemas encode Asset Categories and Instances into their top-level keys.

Abstraction

The Asset Hierarchy can be thought of as a data abstraction governing the schemas, which in turn drive the ECS instantiation.

Metaphysics

An analogy may be drawn from the Asset Hierarchy to Edward Zalta's Metaphysics: Properties encode an Asset, State exemplifies an Asset.

Hierarchy: Category

Asset Categories form the top layer of the hierarchy. Each Asset Category is defined by its static Properties; an Asset's Category determines what type of Properties it will parse from the Property files and inject into its deployment.

Each Category is differentiated by its purpose and place in the semantics of the Engine.

  • Tiles: Environmental. These Assets determine the background and macro-level processes that underlie the Engine.
  • Object: Functional. These Assets perform functions and alter their states.
  • Effects: Periodic. These Assets undergo changes in their state according to fundamental frequencies.
  • Geography: Procedural. These Assets are generated via physical principles embodied by the Engine.
  • Resources: Biological. These Assets undergo lifecycles and have reactive states that change as the result of the environment.
  • Crafts: Structural. These Assets provide the foundation and topology of the Board.
  • Sheets: Intentional. These Assets perform Actions and engage Intentionally with the Board.
  • Widgets: Metalogical. These Assets display metadata about the world to the User.

Hierarchy: Taxonomy

An Asset's order in the Asset Hierarchy is encoded into its Taxonomy. These attributes exist on every Asset instantiated within the game. A Taxonomy is neither a State, a Configuration or a Property. Taxonomy represents the full, unambiguous identity of a deployed Asset,

  • id: str: Uniquely identifies the Asset file. It must match a file found in the src/assets/** directory.
  • name: str: Uniquely identifies the physical deployment of the Asset. Every Asset Instance deployed onto a Board has a unique name.
  • category: str: Determines what Property model is employed by the Asset. The Category must be configured by a src/assets/<category>/**/*.yaml property index file.
  • instance: str: Determines what State model is employed by the Asset. An Asset's state is hydrated from the data/state/<board>/**/*.yaml directory.

(category, instance) collectively map to the components (frame, animation, hitbox, properties, state) injected into an Asset class during the application initialization. More specifically, Category maps to properties (\(\text{category} \to \text{properties}\)), and Instance maps the remaining components (\(\text{instance} \to (\text{frame}, \text{animation}, text{hitbox}, \text{state})\)).

The State and Property model of an Asset can be calculated (and is, during application bootstrapping via Pydantic) from its (Category, Instance)-node, but (Animation, Frame, Hitbox) are independent of the node in the Asset Hierarchy. These components must be specified through a Recipe.

Asset: Architecture

Every rendered entity in the Application is an instance of the unified Asset class. The distinction between a Tile, an Object, or a Sheet is determined entirely by the data models and components injected into them. Behaviors are decoupled from Assets and managed entirely by Mechanic classes that iterate over the Board Assets. See Mechanics documentation for more information.

The formula for an Asset, i.e. the list of components which go into a particular Asset Instance, is specified in its Recipe configuration file. The components of each Assets are enumerated below,

  1. Model: Properties A model defining immutable data.
  2. Model: State A model defining mutable data.
  3. Behavior: Animation Stateless strategies injected into the Asset. These contain the specific logic for updating Animation frames.
    • animate(state, properties): Interface for applying animation logic to Asset state.
  4. Behavior: Frame: A static schema calculation used by the renderer to determine the correct texture string keys.
    • index(id: str, properties: AssetProperties) -> Dict[str, Tuple[int, int, int, int]]: Interface for indexing Asset frames in Registry.
    • keys(id: str, state: AssetState) -> List[Tuple[str, int, int]]: Reflexive intrinsic state projection for dynamic 60 Hz draw passes.
    • eras(id: str, calendar: CalendarState) -> List[Tuple[str, int, int]]: Macro-temporal epochal projection for static pre-rendered canvas baking.
    • channels(id: str, state: AssetState, properties: AssetProperties) -> List[Tuple]: Emits auxiliary shader and texture modulation directives.
  5. Behavior: Hitbox: Stateless collision boundary resolution strategies injected via Recipes. Resolves active physical obstacles dynamically without mutating cached properties:
    • elevations(properties: AssetProperties, state: AssetState) -> List[int]: Emits the discrete elevation tiers the entity participates in.
    • get(properties: AssetProperties, state: AssetState, elevation: int, frame: Optional[Frame] = None) -> List[Hitbox]: Emits active physical collision footprints at the requested elevation, accounting for animation frame states (e.g., Attackboxes).

Stacks and Offsets

An Asset can be a single logical entity composed of multiple superimposed rendered textures, i.e. Sheets, therefore a Frame component returns a List[(str, int, int)] rather than a single str. The tuple (int, int) controls how much the frame is offset from its origin (mainly used in Expressions to pin a Cursor Expressions to the relative Position of a Sprite).

Category: Tiles

  • Property File: /src/assets/tiles/**/*.yaml

Tiles are static Assets that form environmental foundation of the game.

Behavior: Rendering

When a Tile is drawn, it is rendered as a multiple of the unit Tile, usings the Dimensions configured in the Asset directory to expand the multiplied area.

Behavior: Friction

Tiles have coefficients of friction. These coefficient are used by MotionMechanics to determine the rate of velocity decay for Frictive Assets traversing their area.

Properties: TileProperties(AssetProperties)

  • friction: float

Animation: None

N/A

Hitbox: StaticHitbox

  • get(properties, state, frame): returns properties.hitboxes

State: MultiplerState(AssetState)

  • multiple: Multiple

Tile: Environ

A Environ Tile represents the environment. They participate in climatic events and macro-level state changes in the Ecology.

Behavior: Rendering

Tiles have the lowest terrain Substrate; They are always rendered underneath the other Assets in the Hierarchy, regardless any calculations involving elevation, substrate, ground, or priority.

Moreover, they are not included in the core rendering loop; Instead, they are prerendered once and drawn from cache. See Rendering documentation for more information.

Behavior: Seasonality

Environ Tiles undergo Frame changes based on the accumulation of time on the Board. In other words, Environ Tiles have the unique property of having their Frame depend on an external State, rather than internal State. All rendering of Environ Tiles occurs through the Frame.eras() interface to account for this external dependency.

For this reason, Environ Tiles leverage a SeasonalFrame and event-driven reconstruction triggered as the Board undergoes Seasons. See Ecology documentation for more information.

Semantics: Seasons

  • spring
  • summer
  • autumn
  • winter

Atlas: (Row: Season, Column: Period)

  • columns: ^(?:onset|peak|decline)-[0-9]$
  • rows: ^(?:spring|summer|autumn|winter)

Tile: Canopy

Canopy Tiles are hardcoded to always render on on top of all of other Assets, regardless of their elevation or priority.

Widget Exception

The single exception to this rule is Widgets. Canopy Tiles are an "in-world" Asset, and thus their render ordering is superseded by Widgets.

Frame: SingleFrame

  • keys(id, state): returns [ (id, 0, 0) ]
  • index(id, properties): returns { id: (0, 0, properties.dimension.w, properties.dimensions.l) }

Tile: Grid

A Grid is a special Tile reserved for use in the Editor Menu. It is used as an overlay in the Editor, to create a spatial grid that can be traversed through focus.

There must be precisely two Grid tiles:

  • focus: A Grid Tile to represent active selections.
  • cell: A Grid Tile to represent idle selections.

Frame: SingleFrame

  • keys(id, state): returns [ (id, 0, 0) ]
  • index(id, properties): returns { id: (0, 0, properties.dimension.w, properties.dimensions.l) }

Category: Objects

  • Property File: /src/assets/objects/**/*.yaml

Objects are Assets that encapsulate interaction and reaction. Objects participate in CollisionMechanics and may undergo instantaneous changes of their state due to environmental factors. However, Objects do not implement an Animation; All changes of an Object's Frame are handled through the mutation of State attributes.

Field: Count

Objects have different States. count enumerates the number of possible States into which an Object may enter.

  • Unary Objects (count = 1): Crates, Doors, Signs
  • Binary Objects (count = 2): Chests, Gates, Plates

Atlas: (row: Count, column: Material)

  • columns: ^(?:ceramics|chromatics|geologics|metallics|organics)
  • row: ^[0-9]

Properties: ObjectProperties(AssetProperties)

  • hitboxes: List[Hitbox]
  • count: int = 1
  • mass: int
  • materials: Material

State: ObjectState(AssetState)

  • position: Position
  • material: Union[Ceramics, Chromatics, Geologics, Metallics, Organics]

All Objects extend this base Model..

Frame: ObjectFrame

  • index(id, properties): returns { "{id}-{i}": (j * properties.dimension.w, 0, properties.dimensions.w, properties.dimension.l )} for i in partition(properties.material)
  • keys(id, state): returns "{id}-{state.material}"

Animation: None

N/A

Object: Chests

Chests are Objects with a binary state whose Frame can be changed by the Player or Sprite entering the interact Intention while in the immediate proximity of the Chest. When switch == true, the Chest is on (open). When switch == false, the Chest is off (closed).

A Chest is reusable through the interact Intention, meaning Inventory Loot can be taken out of and also placed into a Chest. The content state field manages the current contents of the Chest through a list of Inventory Loot keys.

When interacting with a Chest, the Player is shown the Chest Menu, allowing them to exchange the contents of their Inventory Loot with the contents of the Chest. A Sprite may also enter into an interact Intention with a Chest through its Intention Transition Matrix. This interaction is managed through a dedicated Sprite Mechanic

State: ContainerState

  • switch: bool
  • content: List[str]

Hitbox: StaticHitbox

  • get(properties, state, elevation, frame): returns properties.hitboxes

Frame: BinaryFrame

  • index(id, properties): returns { "{id}-{i}-{j}": (j * properties.dimension.w, i * properties.dimensions.l, properties.dimensions.w, properties.dimension.l )} for i,j in product(properties.count, properties.material)
  • keys(id, state): returns "{id}-{state.material}-{Switches.ON.value}" if state.switch else {id}-{state.material}-{Switches.OFF.value}"

Object: Crates

Crates are Objects who state can be altered by collisions. When acted upon by an external force, momentum is transferred to the Crate and it acquires velocity. See CollisionMechanics for more information on game physics.

State: MotiveState

  • velocity: Velocity

Hitbox: StaticHitbox

  • get(properties, state, elevation, frame): returns properties.hitboxes

Object: Doors

Doors are Objects that alter a Sprite's layer. When a Sprite interacts (state.intention = 'interact') with the hitbox of a Door, the sprite.state.layer is changed to the door.state.outlayer and sprite.state.position is changed to the door.state.out Position.

Behavior: Projection

During hydration, each Door automatically projects a reciprocal shadow footprint onto its state.outlayer at state.out, rendered on a dedicated Substrate (substrate = -1) with a Frame Channel used to filter its appearance.

State: DoorState

  • outlayer: str
  • out: Position
  • projection: LayerProjection

Hitbox: LayeredHitbox

  • elevations(properties, state): returns [] if state.projection == LayerProjection.OUT.value else [max(0, state.elevation or 0)]
  • get(properties, state, elevation, frame): returns properties.hitboxes[state.layer] if LayerProjection.IN.value else properties.hitboxes[state.outlayer]

Object: Gates

Gates are Objects with a binary state linked to Plates. When a Gate is on (open), it does not have hitboxes and dynamic Assets can pass freely through its area. When a Gate is off (closed), its hitboxes prevent dynamic Assets from passing through its area.

Gates do not switch their states of their own accord. A Plate automatically updates the state.switched of its linked Gate, so when the Plate is on, the Gate is on, and when the Plate is off, the Gate is off.

Semantics: Switches

  • on: The Gate is open.
  • off: The Gate is closed.

State: SwitchState

Object: Plates

Plates are Objects with a binary state. Furthermore, that state can be instantaneously altered by collision, e.g. when a Sprite enters its hitbox. When a collision occurs, a Plate will flip its switch. When activated, a Plate in turn notifies the state of its link-keyed Gate to change.

Plate Sensors

Plates must have their mass property configured to be -1, to exclude them from the collision resolution while keeping the collision detection active, i.e. Plates do not move due to collisions, but register when other Assets are intersecting them. Plates are considered Sensors. See CollisionMechanics for more information.

Craft: Bridges

Bridges are Crafts that elevate dynamic Assets over Fluid streams and Shoreline margins without passing through the submerged mutator.

Behavior: Field Suppression

To achieve the functionality of suppressing Fluids fields, broadly speaking, the following occurs,

  • Bridges are registered as Sensors (\(m = -1\)). Therefore, they do not participate in momentum transfer or collisions.
  • Bridges are excluded from the Boards Physics Queries, allowing Mechanics to pathfind across river crossings.
  • In MotionMechanics, intersecting a Bridge marks the Asset as being on a surface:
  • Fluid immersion and current velocity drift are suppressed (\(\vec{v}_{\text{drift}} = \vec{0}\)).
  • Shoreline step-down nudges, ledge constraints, and splash particle emissions are bypassed.
  • mutators.triggers.submerged is cleared to False.

Behavior: Rendering

Bridges belong to a dedicated Substrate, substrate = -1. This guarantees that Bridge areas render above Environ Tiles, Fluids, and Shorelines, while allowing dynamic Assets crossing their area to render above the Bridge via their baseline footprint (\(y + l\)) and the Painter's Algorithm.

Craft: Stairs

Stairs are Crafts that transition the elevation of dynamic Assets.

Behavior: Elevation

The direction of the elevation transition calculation is dependent on the direction of the transitioning Asset's velocity,

  • stairs.state.blueprint == Directions.RIGHT and asset.state.velocity.vx < 0: asset.state.elevation += stairs.state.delta
  • stairs.state.blueprint == Directions.RIGHT and asset.state.velocity.vx > 0: asset.state.elevation -= stairs.state.delta
  • stairs.state.blueprint == Directions.LEFT and asset.state.velocity.vx < 0: asset.state.elevation -= stairs.state.delta
  • stairs.state.blueprint == Directions.LEFT and asset.state.velocity.vx > 0: asset.state.elevation += stairs.state.delta
  • stairs.state.blueprint == Directions.DOWN and asset.state.velocity.vy < 0: asset.state.elevation += stairs.state.delta
  • stairs.state.blueprint == DIRECTION.DOWN and asset.state.velocity.vy > 0: asset.state.elevation -= stairs.state.delta

State: StairState

  • delta: int = 1

Category: Effects

  • Property File: /src/assets/effects/**/*.yaml

Effects are periodic Assets used to encapsulate environmental factors, hazards, pickups, and interactive mechanisms.

Most Effects iterate over a single row of frames using IterableFrame and advance via FrequencyAnimation. The only thing that differentiates each instance of an Effect is its State model (excepting Fluid which plays an instrumental role in Ecology).

Behavior: Periodicity

Rather than implementing separate Animation classes to handle Effect animations (which would lead to a combinatorial explosion with the composition of Animation and State implementations necessary to span the space of possible Effects instances, e.g. HarzardContinuousAnimation, HazardPeriodicAnimation, HazardTemporaryAnimation would have the same functional purpose of being a Hazard but different logic handling their Animation), Effects have Frequencies that determines how their Animation is handled.

In other words, the State Model determines the function of the Effect, but the Frequency determines the Animation update strategy.

Category: Sheets

  • Property File: /src/assets/sheets/**/*.yaml

Sheets are intentional Assets whose Frames are organized into Actions and Directions. Sheets form the core Asset of the Engine Loop; they are used to encapsulate character entities, such as the Player and Non-Playable Sprites. Most of the application is scaffolding for the complex interactions and calculations that occur when Sheet Assets interact with each other and their environment.

Semantics: Directions

  • Directions: up, left, down, right

Direction is part of the Animation State.

Semantics: Actions

  • Action: cast, thrust, walk, slash, shoot, die

Action is part of the Animation State. An Action implicitly contains a Direction, i.e. an Action cannot be specified without an accompanying Direction(s).

Field: Count

  • Count: 0, 1, 2 , ... , n(Action)

Where n(Action) is the number of Frames per Action.

Atlas: (row: (Action, Direction), column: Count)

A Sheet Asset is partitioned along the axes of Direction, Action and Count. Each cell is identified by a tuple (Direction, Action), and then divided horizontally into contiguous horizontal Frames of amount (Count).

Sheet Altas Strictness

For Sheets, it is assumed coordinates of an image in the Asset file are completely determined by Action, Direction and Frame. It is assumed Actions form contiguous rows partitioned by Direction, and Frames are organized in horizontal cells of equal length. This specification is enforced on the application level.

LPC Specification

While an arbitrary Action Set can be defined in /src/data/config/actions/main.yaml, the documentation will often assume the LPC (Liberated Pixel Cup) specification when discussing Action, Direction and Frame, without loss of generality. The values for these fields in the LPC Spec are enumerated below,

The Frames per Action for the LPC Spec are given below,

  • cast: Count = 7
  • thrust: Count = 8
  • walk: Count = 9
  • slash: Count = 6
  • shoot: Count = 13
  • die: Count = 6

Two important points regarding the LPC and worth drawing attention to are given below,

  1. die is only associated with a single row in the LPC specification, i.e. it is a "Directionless" State. By default, the Engine labels it with an up direction.
  2. The thrust Action plays double-duty for spear and shovel. The spear is a Weapon, whereas the shovel is a Tool. With LPC Assets, the Animations of these pieces of Equipment are governed by the thrust Action State. In other words, different types of Equipment do not necessarily map to different Action States. The Engine accounts for this by treating the Equipment Group of Assets as "stateless" and inherently bound to the State of a Sprite Sheet Asset. See Equipment documentation for more information.

Sheet Rows

The row indexing starts at 0.

Model: Action

This snippet from the Schemas shows the general structure of an Action,

<action-key>:
    count: <count>
    delay: <delay>
    directions:
        <direction-key>:
            row: <row>
  • <action-key>: str - Ranges over cast, thrust, walk, slash, shoot, die (LPC)
  • <direction-key> : str - Ranges over up, left, down, right (LPC)
  • count: int - is the number of frames in the Action row grouping.
  • delay: (Optional) Number of Engine ticks to accumulate before a frame update. Used to control the speed of the animation. Defaults to 1.

Each Sheet may specify an ActionSet in its Property index file to use in the construction of its Frame space. See Action Configuration Schema for more details.

Hitbox: Attackboxes

!!! @TODO(10-01) The Hitbox interface has been formally codified into a component of an Asset. Attackboxes are the last remaining legacy hitbox implementation that needs migrated to the new paradigm. They are complicated by their relationship with Equipment and specific Frames in an Animation.

An Attackbox is a special type of hitbox unique to Sheet Assets. It is mapped to a canonical <action>-<direction>-<frame> key (where setting.SEPARATOR = "-") and applied during the animation state identified by this key. Attackboxes are used to augment the Sheet's basic hitbox collision detection during CombatMechanics. While any Sprite can alter its Attackbox properties, this property is utilized mainly by Equipment.

Model: Stack

A Stack is a list of Sheet Asset IDs to superimpose over one another to form the resultant Sheet displayed on the Screen. A Sheet Stack is drawn in the order it is specified, i.e. the first entry has the lowest Z coordinate, with each subsequent entry being stacked on top.

For example, the src/assets/sheets/<sheet-category>/features/hair-blonde-bangs.png might be stacked on top of src/assets/sheets/<sheet-category>/skins/male-dark-human.png to create a new Sheet asset used in the game. This Sprite stack is assembled in the Registry using the stack property during the application bootstrap. The assembled stack is saved as a Sheet Asset, using the <sheet-id> as the Asset key. In other words, once assembled, Stacks are effectively new "virtualized" Assets.

Sheet Stacks

It is assumed all Sheets in a Stack conform to the same (Action, Direction) row mapping.
