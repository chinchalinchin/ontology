### 1. The Problem of Differentia: Why the Hierarchy Is Necessary

In classical genus–differentia definitions (the Porphyrian tree), a **Genus** is partitioned into **Species** by a **Differentia** ($\Delta$)—an attribute possessed by that subset and no sibling subset:

$$\text{Species} = \text{Genus} \cap \Delta$$

In `ontology`, `AssetProperties` (`dimensions`, `priority`) and `AssetState` (`id`, `name`, `layer`, `elevation`, `anchor`, `mutators`) form the summum genus. The Categories and Instances are defined by mutually exclusive differentiae:

| Genus / Species (`Category` / `Instance`) | Static Differentia ($\Delta_P \subset \text{Properties}$) | Dynamic Differentia ($\Delta_S \subset \text{State}$) | Governing Mechanic |
| --- | --- | --- | --- |
| **`tiles.*`** | `friction: float` | `multiple: Multiple` | `MotionMechanics` (`frictive.py`) |
| **`effects.*`** | `lifecycle: Lifecycle`, `count: int` | `animation: AnimationState` (+ `Damage`, `Lot`, `Flow`) | `AnimationMechanics`, `FluidMechanics` |
| **`resources.*`** | `lifespan: Lifespans`, `loot: str` | `stage: str`, `retention: float`, `moisture_flux: float` | `SeasonMechanics` |
| **`crafts.*`** | `cost: List[Cost]` | `owner: str` (+ `direction`, `orientation`, `delta`) | `Decomposer`, `CollisionMechanics` |
| **`sheets.*`** | `actions: Dict`, `stack: List`, `attackboxes: Dict` | `intention`, `goal`, `trajectory`, `inventory`, `meters` | `Cognition`, `Transition`, `Navigation`, `Combat` |
| **`objects.doors`** | — | `outlayer: str`, `out: Position` | `InteractionMechanics` |
| **`objects.gates / plates`** | `count: int = 2` | `switch: bool`, `link: str` | `SwitchMechanics` |

Your critique of "Axis 4" (capability queries) exposes a fundamental type-theoretic constraint: **because differentiae are mutually exclusive across sibling classes, a Mechanic cannot query a differentia without first restricting its domain to the Genus or Species that defines it.**

If you attempt to eliminate `(Category, Instance)` queries in favor of universal capability queries, you are forced into one of two anti-patterns:

1. **Runtime Reflection (`getattr` / `hasattr`):** Every Mechanic must probe unknown objects dynamically (e.g., `getattr(asset.properties, "lifecycle", None)` in `Board.serialize()`), forfeiting static type guarantees.
2. **Root Schema Pollution:** Every differentia (`friction`, `lifecycle`, `lifespan`, `cost`, `actions`, `outlayer`, `switch`) must be pushed up into the base `AssetProperties` and `AssetState` classes as `Optional[...] = None`, destroying the schema validation that prevents a `Tile` from having `attackboxes` or a `Sign` from having `moisture_flux`.

Therefore, `board.categories(...)` and `board.instances(...)` are not redundant wrappers; they are **domain projections** that narrow the universal `Asset` type to the exact subtype where a Mechanic's required differentia is guaranteed to exist.

#### Where the Porphyrian Tree Currently Leaks: Cross-Cutting Traits vs. True Differentiae

The only place where the hierarchy creates friction is when an attribute is **not** a unique differentia of one Category, but is duplicated across multiple sibling Categories as if it were:

* In `src/app/models/properties.py`, `mass: int` and `hitboxes` are re-declared independently across six sibling classes (`EffectProperties`, `ObjectProperties`, `CraftProperties`, `ResourceProperties`, `GeographyProperties`, `SheetProperties`).
* Meanwhile, `CursorProperties` (`src/app/models/properties.py`) omits `hitboxes` entirely, even though `recipes.yaml` assigns `hitbox: static` to `cursors.projectiles`—meaning `StaticHitbox.get()` will raise an `AttributeError` on a `Projectile` if it accesses `properties.hitboxes` directly.

Introducing a single intermediate subaltern genus in `src/app/models/properties.py` separates **non-spatial assets** (`TileProperties`, `CursorProperties`, `WidgetProperties`) from **spatial collider assets**:

```python
@dataclass(slots=True)
class AssetProperties:
    dimensions: Dimensions
    priority: int = 0

@dataclass(slots=True)
class SpatialProperties(AssetProperties):
    mass: int = -1
    hitboxes: Optional[HitboxSpec] = None

```

When `ObjectProperties`, `CraftProperties`, `EffectProperties`, `ResourceProperties`, `GeographyProperties`, `SheetProperties`, and `ProjectileProperties` inherit from `SpatialProperties`, `mass` and `hitboxes` become guaranteed attributes of the subaltern genus, while `cost`, `lifecycle`, `lifespan`, and `actions` remain strict Category differentiae.

### 2. Hydrating `HitboxSchema` via Pydantic Without Re-Segregating Categories

You identified two obstacles to hydrating `HitboxSchema` directly through the Pydantic property schema:

1. **The Category Sharing Problem:** `Category` maps to `Properties` (`crafts -> CraftProperties`), but instances within `crafts` use different hitbox schemas (`platforms -> ElevatedHitbox`, `stairs -> DirectedHitbox`, `railings -> OrientedHitbox`, `struts/bridges -> StaticHitbox`).
2. **The `DynamicHitbox` Problem:** `fluids` and `shorelines` store mutable `hitboxes` on `AssetState`, overriding `AssetProperties`.

Both obstacles can be resolved cleanly in Python without splitting `crafts` into multiple Categories and without keeping `hitbox:` in `recipes.yaml`.

#### Solution to Obstacle 1: Generic Parameterization on `*PropertyInstances`

Look at `CraftPropertyInstances` in `src/app/models/properties.py`:

```python
@dataclass(slots=True)
class CraftPropertyInstances:
    struts: Dict[str, CraftProperties] = field(default_factory=dict)
    bridges: Dict[str, CraftProperties] = field(default_factory=dict)
    platforms: Dict[str, CraftProperties] = field(default_factory=dict)
    stairs: Dict[str, CraftProperties] = field(default_factory=dict)

```

Notice that `PropertiesSchema` *already* has an explicit node for every `(category, instance)` pair (`struts`, `bridges`, `platforms`, `stairs`)! The only reason all four currently receive the same `Union[...]` hitbox type is that `CraftProperties` is not parameterized by a type variable `Generic[H]`.

If each `HitboxSchema` is a Pydantic-validated dataclass (or custom validator type) that wraps its underlying data structure and implements `.elevations(state)` and `.get(state, elevation, frame)`, then `CraftProperties[H]` can be parameterized per instance node in `CraftPropertyInstances` without creating new Category classes:

```python
from dataclasses import dataclass, field
from typing import Dict, Generic, List, Optional, TypeVar
from libs.core.models import Dimensions, Hitbox, Position

H = TypeVar("H", bound="BoundHitbox")

class BoundHitbox:
    def elevations(self, dimensions: Dimensions, state: AssetState) -> List[int]:
        return [max(0, state.elevation if state.elevation is not None else 0)]

    def get(self, dimensions: Dimensions, state: AssetState, elevation: int) -> List[Hitbox]:
        return []

@dataclass(slots=True)
class StaticHitboxSpec(BoundHitbox):
    boxes: Optional[List[Hitbox]] = None

    def get(self, dimensions: Dimensions, state: AssetState, elevation: int) -> List[Hitbox]:
        target_e = max(0, state.elevation if state.elevation is not None else 0)
        if max(0, elevation) != target_e:
            return []
        if self.boxes is None:
            return [Hitbox(Position(0, 0), dimensions)] if dimensions else []
        return self.boxes

@dataclass(slots=True)
class ElevatedHitboxSpec(BoundHitbox):
    tiers: Dict[int, List[Hitbox]] = field(default_factory=dict)

    def elevations(self, dimensions: Dimensions, state: AssetState) -> List[int]:
        base_e = state.elevation if state.elevation is not None else 0
        return [base_e + k for k in self.tiers.keys()] if self.tiers else [base_e]

    def get(self, dimensions: Dimensions, state: AssetState, elevation: int) -> List[Hitbox]:
        base_e = state.elevation if state.elevation is not None else 0
        return self.tiers.get(elevation - base_e, [])

@dataclass(slots=True)
class DirectedHitboxSpec(BoundHitbox):
    directions: Dict[str, List[Hitbox]] = field(default_factory=dict)

    def get(self, dimensions: Dimensions, state: AssetState, elevation: int) -> List[Hitbox]:
        target_e = max(0, state.elevation if state.elevation is not None else 0)
        if max(0, elevation) != target_e:
            return []
        return self.directions.get(state.direction, [])

```

Now `CraftProperties[H]` remains a single Category property model, while `CraftPropertyInstances` binds the exact hitbox schema at each instance node:

```python
@dataclass(slots=True)
class CraftProperties(AssetProperties, Generic[H]):
    cost: List[Cost] = field(default_factory=list)
    mass: int = 0
    hitboxes: H = None  # Hydrated by Pydantic using the concrete type bound in CraftPropertyInstances

@dataclass(slots=True)
class CraftPropertyInstances:
    struts: Dict[str, CraftProperties[StaticHitboxSpec]] = field(default_factory=dict)
    bridges: Dict[str, CraftProperties[StaticHitboxSpec]] = field(default_factory=dict)
    platforms: Dict[str, CraftProperties[ElevatedHitboxSpec]] = field(default_factory=dict)
    stairs: Dict[str, CraftProperties[DirectedHitboxSpec]] = field(default_factory=dict)
    railings: Dict[str, CraftProperties[OrientedHitboxSpec]] = field(default_factory=dict)

```

1. **Zero Category Re-segregation:** `crafts` remains a single Category with a single `CraftProperties` class.
2. **Compile-Time Schema Validation:** If a user accidentally puts a flat `List[Hitbox]` into `platforms/main.yaml` instead of a tier-keyed `Dict[int, List[Hitbox]]`, Pydantic fails immediately at bootstrap during `CraftProperties[ElevatedHitboxSpec]` validation.

#### Solution to Obstacle 2: `DynamicHitbox` as State-Over-Property Precedence

Inspect `DynamicHitbox.get()` in `src/app/assets/hitboxes/core.py`:

```python
class DynamicHitbox(HitboxSchema):
    def get(self, properties, state, elevation, frame=None) -> List[Hitbox]:
        target_e = max(0, state.elevation if state.elevation is not None else 0)
        if max(0, elevation) != target_e:
            return []
        if state.hitboxes is None:
            if properties.hitboxes is None:
                if properties.dimensions:
                    return [Hitbox(Position(0, 0), properties.dimensions)]
                return []
            return properties.hitboxes
        return state.hitboxes

```

`DynamicHitbox` does not define a new geometric structure—it is strictly **state-level shadowing**: if `state.hitboxes` is populated on `FluidState` or `ShorelineState`, use `state.hitboxes`; otherwise fall back to `properties.hitboxes`.

If `FluidState.hitboxes` and `ShorelineState.hitboxes` are typed as `Optional[StaticHitboxSpec] = None` (or `Optional[List[Hitbox]] = None`), then `Asset` in `src/app/assets/base.py` resolves state shadowing natively in two lines without a separate `DynamicHitbox` strategy class:

```python
class Asset:
    @property
    def hitboxes(self) -> List[Hitbox]:
        state_hb = getattr(self.state, "hitboxes", None)
        if state_hb is not None:
            target_e = max(0, self.elevation)
            return state_hb if max(0, self.elevation) == target_e else []
        if hasattr(self.properties, "hitboxes") and self.properties.hitboxes is not None:
            return self.properties.hitboxes.get(self.dimensions, self.state, self.elevation)
        return []

```

Under this formulation:

* `PropertiesSchema` nodes hydrate `properties.hitboxes` via `Generic[H]` into the exact `BoundHitbox` subtype.
* `StateSchema` nodes for `fluids` and `shorelines` shadow `properties.hitboxes` whenever `state.hitboxes` is non-null.
* `recipes.yaml` only needs to map `(frame, animation)`—the two components that interpret raw pixel coordinates and temporal tick progression, which genuinely exist outside the data schema.
